# `pragma-ai workflow` command reference

`pragma-ai workflow` is a command group for tracking local executions of AI-IDE
workflow assets (Kiro, Claude Code, GitHub Copilot). A "workflow" here is an
IDE asset defined outside this repo (Mimir-delivered) that runs an ordered
sequence of steps/actions — `pragma-ai-cli` does not define those workflows,
it is *invoked by* them, as one of their step actions, to report progress and
surface human-edit gaps to observability.

None of these commands are wired to IDE hooks. Every one of them must be
called explicitly by the workflow asset itself, on every IDE, as a step
action. See [`design/features/gap-calculator-local-workflow.md`](features/gap-calculator-local-workflow.md)
for the full design rationale.

State (instances, steps, baselines) is stored locally under `~/.pragma/`,
keyed by the project directory — never inside the project's own `.pragma/`
folder, so a misbehaving workflow action can't tamper with its own recorded
progress. `workflow list`/`workflow status` read only this local state; they
are not a front-end for the observability backend, which is write-only from
this CLI's perspective.

## Command summary

| Command | Purpose |
|---|---|
| [`workflow create`](#workflow-create) | Start a new workflow instance; mints and prints its ID |
| [`workflow report`](#workflow-report) | Report one step's progress (started/paused/finished/failed) |
| [`workflow gap-report`](#workflow-gap-report) | Compute and submit the human-edit gap for a finished step |
| [`workflow list`](#workflow-list) | List known workflow instances for the project |
| [`workflow status`](#workflow-status) | Show one instance's full step-by-step detail |

## Typical flow

```bash
# 1. Start the instance once, at the top of the workflow
instance_id=$(pragma-ai workflow create --workflow-id contract-review)

# 2. Report each step as the workflow executes it
pragma-ai workflow report --instance-id "$instance_id" --workflow-id contract-review \
  --step-id extract-schema --status started

pragma-ai workflow report --instance-id "$instance_id" --workflow-id contract-review \
  --step-id extract-schema --status finished --output-file schemas/contract.json

# 3. If a human edits that step's output before the next step runs, compute
#    the gap (phase A), then submit the agent's interpretation (phase B)
pragma-ai workflow gap-report --instance-id "$instance_id" --step-id extract-schema
pragma-ai workflow gap-report --instance-id "$instance_id" --step-id extract-schema \
  --submit --report-id <id-printed-by-phase-A> --summary "Analyst renamed field X to Y."

# 4. Inspect progress at any time
pragma-ai workflow status "$instance_id"
pragma-ai workflow list --status started
```

Every command accepts `--project-dir <path>` (defaults to the current working
directory) and `--skip-auth` (skips login; requires `PRAGMA_TEST_ACCESS_TOKEN`,
intended for tests/CI, not normal use).

## `workflow create`

Mints a `workflow_instance_id` (UUID), links it to the authenticated user
and — if the project is a git repo — the current branch, persists that state
locally, and emits the workflow-level `workflow_started` event to
observability.

```bash
pragma-ai workflow create --workflow-id <name> [--user-story-id <id>] [--project-dir <path>] [--skip-auth]
```

| Flag | Required | Notes |
|---|---|---|
| `--workflow-id` | yes | The IDE workflow asset's own name/identifier. |
| `--user-story-id` | no | Human-meaningful correlation key (e.g. a ticket ID) shared across *multiple instances* of the same or related work. Not generated by the CLI. |
| `--project-dir` | no | Defaults to cwd. |
| `--skip-auth` | no | Test-only. |

**Output contract:** stdout gets *only* the minted instance ID — nothing
else. This is load-bearing: the workflow asset is expected to capture that
stdout and forward it as `--instance-id` to every later `workflow report` /
`workflow gap-report` call for the rest of the run. Human-readable context
(which workflow, which branch) goes to stderr instead, so it never pollutes
the captured value.

**Re-running a workflow** (e.g. retrying the whole thing after it failed) means
calling `workflow create --user-story-id <id>` again to mint a fresh instance
— not reusing a `step-id` inside an existing instance.

## `workflow report`

Reports one step's status within an instance minted by `workflow create`.
`duration_ms` is always computed by the CLI from the step's locally persisted
`started_at` — never accepted from the caller.

```bash
pragma-ai workflow report --instance-id <id> --workflow-id <name> --step-id <id> \
  --status <started|re_started|paused|finished|failed> \
  [--output-file <path>]... [--project-dir <path>] [--skip-auth]
```

| Flag | Required | Notes |
|---|---|---|
| `--instance-id` | yes | The ID printed by `workflow create`. |
| `--workflow-id` | yes | Must match the instance's own workflow ID, or the command errors. |
| `--step-id` | yes | The step/action identifier — any string the workflow asset chooses. |
| `--status` | yes | See status state machine below. |
| `--output-file` | no, repeatable | Relative to `--project-dir`. **Only valid with `--status finished`.** Snapshots the named file(s) as this step's gap baseline for a later `workflow gap-report`. |

### Status state machine (per `step-id`, within one instance)

| From → `--status` | Behavior |
|---|---|
| *(new step)* → `started` | Creates the step, attempt `1`. |
| `started`/anything → `started` again | **Error.** A step_id can't be `started` twice in the same instance — use `re_started` to resume/retry it, or start a fresh instance for a new run. |
| *(existing step)* → `re_started` | Increments `attempt`, resets `started_at` to now, clears any prior `finished_at`/`duration_ms`. Errors if the step was never `started`. |
| *(existing step)* → `paused` | Marks the step paused — a deliberate, resumable halt, distinct from `failed`. A different actor (different authenticated user) can later `re_started` it. Errors if the step was never `started`. |
| *(existing step)* → `finished` / `failed` | Terminal. Computes `duration_ms = now - started_at`. Errors if the step was never `started`. |

`--output-file` is rejected outside `--status finished` (the CLI returns an
error rather than silently ignoring it).

## `workflow gap-report`

Two-phase hand-off, mirroring `pragma-ai kayros gap-report`'s design but
sourced from a step's local baseline instead of a Kayros export. This is how
a workflow captures human intervention on a step's output — the CLI never
interprets the diff itself; it hands the diff to the calling agent and waits
for the agent's natural-language interpretation.

### Phase A — generate

```bash
pragma-ai workflow gap-report --instance-id <id> --step-id <id> [--project-dir <path>]
```

Requires that the step was already reported `finished` with at least one
`--output-file` (via `workflow report`) — that call is what captured the
baseline this command diffs against. Loads that baseline, computes the gap
against the file(s) as they exist now, and prints to stdout:

- a freshly minted `Report ID`
- a fenced, agent-readable unified diff of what changed since the baseline
- instructions telling the calling agent to interpret the diff and submit it
  via Phase B, referencing this same Report ID and the exact `--submit`
  command to run

No Hub call, no MCP involvement — this is purely local diff computation. If
nothing changed, it says so and instructs the agent *not* to call `--submit`
for that report ID.

### Phase B — submit

```bash
pragma-ai workflow gap-report --instance-id <id> --step-id <id> \
  --submit --report-id <id-from-phase-A> (--summary "<text>" | --summary-file <path>) \
  [--project-dir <path>] [--skip-auth]
```

| Flag | Required | Notes |
|---|---|---|
| `--report-id` | yes (with `--submit`) | Must be the ID Phase A printed. |
| `--summary` | one of these two | The agent's natural-language interpretation of the human edit. |
| `--summary-file` | one of these two | Read the interpretation from a file instead of inlining it. |

Validates the summary against the same content guard the Kayros gap-report
pipeline uses (rejects code/diff hunks, file paths, secret-shaped values —
only aggregate counts and prose ever leave the machine), re-computes the gap,
persists the interpretation locally, links `gap_report_id` onto the step (so
`workflow status` can show it), and emits a `workflow_gap_report` event to
observability — self-linked to the step's own progress reporting via the
shared `gap_report_id`.

## `workflow list`

Lists known workflow instances for the project from local state.

```bash
pragma-ai workflow list [--status <started|paused|finished|failed>] [--user-story-id <id>] \
  [-o table|json] [--project-dir <path>]
```

| Flag | Notes |
|---|---|
| `--status` | Filters by *derived* status (see below), not the raw stored value. |
| `--user-story-id` | Filters to instances sharing that correlation key. |
| `-o, --output` | `table` (default) or `json`. |

**Derived status** is computed from an instance's steps, not read verbatim
from storage (an instance's persisted status stays `started` forever — there
is no `workflow finish`/`workflow fail` command):

- any step `failed` → instance shows `failed`
- no steps in a non-terminal state (all `finished`) → instance shows `finished`
- any step `paused` (and none failed) → instance shows `paused`
- otherwise → `started`

## `workflow status`

Detail view of one instance: every step reported so far, its status,
attempt count, duration, and any linked gap report ID.

```bash
pragma-ai workflow status <instance-id> [--project-dir <path>]
```

Takes the instance ID as a positional argument (unlike every other
subcommand, which takes it as `--instance-id`). Prints the instance's
workflow ID, user story ID and branch (if set), start time, derived status,
and then one line per step, sorted by step ID, e.g.:

```
Instance:     3f9c2b1a-...
Workflow:     contract-review
User story:   JIRA-1234
Branch:       feature/contract-review
Started:      2026-08-29 14:02:11 UTC
Status:       started

  extract-schema                finished    attempt 1      842ms  gap_report_id=91a...
  validate-schema                started    attempt 1        0ms
```

Use this to check whether a paused instance is safe to resume, and by whom
— any user can query any instance's local state on the machine that ran it
(hand-off across machines relies on the `branch` field plus the assumption
that step outputs are committed; see the design doc's "Workflow state
storage" section for the caveats).
